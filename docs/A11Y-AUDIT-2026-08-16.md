## P0 — Blocking, straight WCAG A/AA failures

### P0-1 · `<html lang>` never matches the rendered language — WCAG 3.1.1 (A)

**File:** [`src/i18n/index.ts:68`](../src/i18n/index.ts)

`document.documentElement.lang` is assigned **only** inside the `languageChanged` handler, and that handler is registered *after* `i18n.init()`. The init-time language change therefore never fires it.

**Measured** — real browser, three locales, homepage:

| Browser locale | Rendered `<h1>` | `<html lang>` |
|---|---|---|
| `de-DE` | „Programmiere deine Musik live" | **`en`** |
| `es-ES` | «Programa tu música en vivo» | **`en`** |
| `en-US` | "Live code your music" | `en` (accidentally correct) |

A German user gets a fully German page announced by an English screen-reader voice. It only self-corrects after a manual click on the language switcher (`→ de` verified). This also mislabels `og:locale` for every share.

**Fix** — one line, immediately after the `.init({...})` call:

```ts
document.documentElement.lang = i18n.language
```

Keep the existing handler for subsequent switches. Guard it in `src/App.test.tsx` or a new `src/i18n/locales.test.ts`.

### P0-2 · `color-contrast` — 4 602 nodes, but only 4 real decisions

**Rule:** `color-contrast` (serious, WCAG 1.4.3 AA) · every route, both viewports
**Files:** [`src/styles/tokens/colors.css:29`](../src/styles/tokens/colors.css), `:37`, `:27`

Computed contrast matrix against the repo's real tokens (`✓` ≥ 4.5, `~` 3.0–4.49, `✗` < 3.0):

| foreground | `--color-bg` `#09090b` | `--color-bg-alt` `#18181b` | `--color-bg-elevated` `#27272a` | `--color-bg-hover` `#3f3f46` |
|---|---|---|---|---|
| `--color-text` `#fafafa` | ✓ 19.06 | ✓ 16.97 | ✓ 14.27 | ✓ 10.01 |
| `--color-text-secondary` `#a1a1aa` | ✓ 7.76 | ✓ 6.91 | ✓ 5.81 | ~ 4.07 |
| **`--color-text-muted` `#71717a`** | **~ 4.12** | **~ 3.67** | **~ 3.08** | **✗ 2.16** |
| **`--color-primary` `#a855f7`** | ✓ 5.03 | **~ 4.48** | **~ 3.76** | **✗ 2.64** |
| `--color-error` `#ef4444` | ✓ 5.29 | ✓ 4.71 | ~ 3.96 | ✗ 2.78 |

The four decisions, in order of blast radius:

**(a) `--color-text-muted` fails on every background — ~1 500 nodes.**
`#71717a` never reaches 4.5:1 anywhere. Worst real instance: `#71717a` on `#27272a` = **3.08** (418 nodes, `/samples` + `/examples` card descriptions).
**Fix:** raise the token to **`#8d8d95`** — that clears 4.5:1 on `bg` (5.1), `bg-alt` (4.9) *and* `bg-elevated` (4.52) with one edit. Reserve `--color-text-muted` for ≥ `bg-elevated` and never place it on `--color-bg-hover` (would need `#aaaab2`).

**(b) `--color-primary` used as body text — ~280 nodes.**
`#a855f7` on `--color-bg-alt` = **4.47** — it misses by 0.03. On `--color-bg-elevated` = 3.76.
**Fix:** add a dedicated ink token (the pattern already used in the hundeschule dual-theme work) — `--color-primary-ink`, a lightened purple that clears 4.5:1 on `bg-elevated`, used wherever purple is *text*. Keep `--color-primary` for fills, borders and the focus ring, where 3:1 (WCAG 1.4.11) is the bar and it already passes.
Hot spots: [`src/components/organisms/StatusBar.tsx:162`](../src/components/organisms/StatusBar.tsx) ("What's New"), `/samples` card `<h3>`s (190 nodes), `/changelog` inline `<code>`.

**(c) White text on saturated badge fills — ~30 nodes, the worst ratios in the app.**
`--color-text` `#fafafa` on `--color-success` `#22c55e` = **2.18**. On `--color-warning` = 2.06. On `--color-error` = 3.61. On `--color-primary` = 3.79.
**Fix is trivial and total:** flip badge ink to **dark**. `#09090b` on those same fills gives **8.73 / 9.26 / 5.29 / 5.03** — all pass comfortably. Add `--color-on-accent: var(--color-bg)` and use it for every filled badge/pill.
Hot spots: `/changelog` version + type badges, `/blog` tag pills, the language switcher's active state ([`LanguageSwitcher`](../src/components/molecules/LanguageSwitcher.tsx), measured `#0c0c0e` on `#8b49cb` = **3.64**, present on all 12 routes).

**(d) Compounding opacity.** `/sessions` renders `#62626a` on `#27272a` = **2.46** — that is `--color-text-muted` with an extra `opacity: 0.8` on top. Once (a) lands, drop the redundant `opacity` rather than re-tinting.

### P0-3 · Two unnamed modal dialogs stack over `/editor` on first visit, and Escape does not dismiss the first

**Files:** [`src/components/organisms/TemplateSelector.tsx:41`](../src/components/organisms/TemplateSelector.tsx), [`:76`](../src/components/organisms/TemplateSelector.tsx) · [`src/components/organisms/TutorialOverlay.tsx:55`](../src/components/organisms/TutorialOverlay.tsx)

Measured on a clean profile at `/editor`: `TemplateSelector` ("Choose a starter template") opens immediately, and after dismissal `TutorialOverlay` ("1 / 4 — Write Your Code") opens behind it. Both are `role="dialog" aria-modal="true"`.

Measured facts:

- `aria-dialog-name` violation (serious) — `TemplateSelector` has **no accessible name**: `aria-label` and `aria-labelledby` both `null`. Same for [`ShareDialog.tsx:79`](../src/components/molecules/ShareDialog.tsx) and [`GistDialog.tsx:173`](../src/components/organisms/GistDialog.tsx). Only `TutorialOverlay` is named. A screen reader announces "dialog" with no title.
- **Escape does not close `TemplateSelector`** — measured `false` even with focus confirmed inside the dialog. The `Escape` branch sits on a React `onKeyDown` on the backdrop `<div>` (`:41`), so it depends on the event bubbling from whichever child holds focus, and it does not reliably do so on first paint. WCAG 2.1.2 expects a keyboard exit from a modal.
- 66 focusable elements **outside** the dialog remain in the tab order. `aria-modal="true"` is a promise to AT, not an enforcement — the background is neither `inert` nor `aria-hidden`. The hand-rolled JS Tab-cycle at `:39-57` is the only guard, and it is bypassed by screen-reader virtual cursor and by browser find-in-page.

**Fix:** give all four dialogs `aria-labelledby` pointing at their existing `<h2>`; add a `document`-level `keydown` Escape listener while open; set `inert` on the app root while a modal is open (baseline in all current browsers) instead of relying on the manual Tab cycle. Consider whether a first-run user needs *two* sequential modals at all.

### P0-4 · Focus is destroyed when any dialog closes — WCAG 2.4.3 (A)

**Files:** [`ShareDialog.tsx:45-52`](../src/components/molecules/ShareDialog.tsx), [`GistDialog.tsx:68`](../src/components/organisms/GistDialog.tsx), [`TemplateSelector.tsx:30-37`](../src/components/organisms/TemplateSelector.tsx)

All three move focus *into* the dialog on mount (measured: `focusInDialog = true` — that part is correct) but **none stores the previously-focused element**, so on close focus lands on `<body>`.

**Measured:** focus Share button → open → Escape → `document.activeElement` is **`BODY (lost)`**. A keyboard user is dumped to the top of a 67-control page and must re-tab from scratch. Every dialog close in the app does this.

**Fix:** the standard three lines — capture `document.activeElement` in the open effect, restore it in the cleanup. Best extracted once into a `useDialog()` hook in `src/lib/`, since four components repeat the same trap code verbatim (they are already near-identical copies — a real DRY violation, not just an a11y one).

### P0-5 · `/legal` — broken tab control and a hash that never re-reads

**File:** [`src/pages/Legal.tsx:17-19`](../src/pages/Legal.tsx)

Two measured violations on this route, plus a routing defect. This route carries the **Impressum and Datenschutzerklärung** — under §5 DDG and DSGVO Art. 13 it is the last page that should be broken.

1. `aria-valid-attr-value` (**critical**): `#tab-impressum` has `aria-controls="tabpanel-impressum"`, but the panel's actual `id` is **`legal-content`**. The reference dangles, so the tab↔panel relationship does not exist for AT.
2. `aria-allowed-role` (minor): `role="tabpanel"` is applied to an `<article>`, which does not permit it.
3. **The hash is read once, at mount.** `useState(location.hash === '#datenschutz' ? …)` is a lazy initializer with no `useEffect` on `location.hash`. Clicking "Datenschutz" in the StatusBar ([`StatusBar.tsx:167`](../src/components/organisms/StatusBar.tsx)) while already on `/legal` changes the URL and **does not switch the tab** — the user is silently left on the Impressum. From any other page it works.

**Fix:** `id="tabpanel-impressum"` on the panel (or point `aria-controls` at `legal-content`), swap `<article>` → `<div role="tabpanel">`, and add `useEffect(() => setTab(...), [location.hash])`.

## P1 — Serious

### P1-1 · Alt+1…9 and Shift+Alt+1…9 are dead on macOS — 18 of the app's shortcuts

**File:** [`src/components/organisms/StrudelEditor.tsx:459-480`](../src/components/organisms/StrudelEditor.tsx)

This is a **library-source finding confirmed by a targeted runtime test**, and it is easy to get a false pass on: Playwright's synthetic `Alt+1` sends `key: '1'`, which works. A real Mac does not send that.

CodeMirror's key resolver, `node_modules/@codemirror/view/dist/index.cjs:9141-9145`, contains an explicit carve-out:

```js
// Alt-combinations on macOS tend to be typed characters
!(browser.mac && event.altKey && !(event.ctrlKey || event.metaKey)) &&
(baseName = w3cKeyname.base[event.keyCode]) && baseName != name
```

CM6 deliberately **refuses** the `event.keyCode` fallback on macOS when Alt is held without Ctrl/Meta. On macOS, Option+1 produces `event.key === '¡'`, so the lookup for `Alt-1` never matches and there is no recovery path.

**Measured**, dispatching the events a real Mac produces, into the live editor:

| Event | `defaultPrevented` (binding fired?) |
|---|---|
| `Alt-1`, `key:"1"` (Windows / Linux) | **`true`** — works |
| `Alt-1`, `key:"¡"` (**real macOS**) | **`false`** — dead |
| `Shift-Alt-1`, `key:"⁄"` (**real macOS**) | **`false`** — dead |

All 9 solo and all 9 mute bindings are unreachable on the primary platform for this app. (Independently, `ARCHITECTURE §5.11` records that these bindings mutate a `Set` nothing reads — so fixing the keymap alone will not make them *do* anything. Both layers need work; do not fix one and report success.)

**Fix:** bind by physical key via `code` — CM6 supports this through a custom `keydown` handler, or rebind to a mac-safe combo (`Ctrl-1..9`). Then verify on a real Mac, not in a headless synthetic-event harness.

### P1-2 · `onKey()` hijacks Cmd+S / Ctrl+S — WCAG 2.1.4 (A)

**File:** [`src/lib/strudel-extensions.ts:82-94`](../src/lib/strudel-extensions.ts)

`onKey` is exposed to user pattern code and is documented at `SidePanel.tsx:670`. Its `document` listener guards `INPUT` / `TEXTAREA` / `.cm-content`, but **never inspects modifiers**.

**Measured** with a binding registered exactly as user code would (`window.onKey('s', cb)`), events dispatched on `<body>`:

| Event | callback fired | `preventDefault()` |
|---|---|---|
| `s` | ✓ | `true` |
| **`Cmd+S`** | **✓** | **`true`** |
| **`Ctrl+S`** | **✓** | **`true`** |

So any session using `onKey('s', …)` silently swallows Save on both platforms. The same applies to every letter the user binds — `onKey('f')` eats Cmd+F (find), `onKey('a')` eats Cmd+A. This is WCAG 2.1.4 **Character Key Shortcuts**, which requires single-character shortcuts to be remappable or focus-scoped; here they are neither, and they additionally capture modified combos they were never meant to see.

Note the collision is **conditional on user code registering a binding** — with no bindings registered, nothing fires (measured `false`). The architecture doc's framing is right about the mechanism; this adds the precondition.

**Fix:** first line of the handler — `if (e.metaKey || e.ctrlKey || e.altKey) return`. [`VirtualKeyboard.tsx:203`](../src/components/atoms/VirtualKeyboard.tsx) already does exactly this and is correct; copy it.

### P1-3 · CodeMirror Tab behaviour — passes 2.1.2, fails its advisory clause

**File:** [`src/lib/editor/setup.ts:63`](../src/lib/editor/setup.ts) (`indentWithTab`)

Honest result, measured:

| Action | Outcome |
|---|---|
| Click editor, press Tab | Focus **stays** in `.cm-content`; two spaces inserted into the document |
| Press Escape, then Tab | Focus **escapes** to the resize handle ✓ |

So this is **not** a hard keyboard trap — CM6's standard Escape-then-Tab hatch works. WCAG 2.1.2 is therefore met on the "can focus leave" clause, but 2.1.2 *also* requires that where the exit method is non-standard, **the user is advised of it**. Nothing in the UI, the help panel or `src/data/docs.ts` mentions Escape-then-Tab.

I am deliberately not filing this as "remove `indentWithTab`" — Tab-indents-code is correct behaviour for a code editor and removing it would be a worse product.

**Fix (cheap, honest):** document Escape-then-Tab in the shortcuts help (`SidePanel`/`HelpPanel`) and add it to `src/data/docs.ts`. Optionally surface a one-time hint on first editor focus.

## P2 — Moderate

### P2-1 · Reduced motion is declared but not honoured where it matters — WCAG 2.2.2 / 2.3.3

**Files:** [`src/styles/global.css:169-177`](../src/styles/global.css), [`src/components/atoms/CanvasVisualizer.tsx:41-64`](../src/components/atoms/CanvasVisualizer.tsx)

`global.css` has a correct, thorough `prefers-reduced-motion` reset — but it can only disable **CSS** animations and transitions. The visualizers are `requestAnimationFrame` loops in JavaScript and are completely untouched by it.

**Measured** on `/editor`, idle, **not playing**:

| Condition | rAF callbacks / sec |
|---|---|
| `prefers-reduced-motion: no-preference` | **360** |
| `prefers-reduced-motion: reduce` (`matchMedia` confirmed `true`) | **360 — identical** |
| after `visibilitychange` → `hidden` | **360 — identical** |

360 rAF/s ÷ 60 fps ≈ **6 concurrent animation loops** running on an idle editor with nothing playing, on battery, regardless of user preference. `grep` confirms **zero** `visibilitychange` / `document.hidden` handlers anywhere in `src/`, and the only two `prefers-reduced-motion` hits in the repo are the CSS block itself.

**On the seizure question (WCAG 2.3.1) — honest assessment: not a failure.**
- `.cm-eval-flash` ([`global.css:286`](../src/styles/global.css)) is a single soft `color-mix(... 15%)` fade over `--transition-slow`. One fade per evaluation is nowhere near the "three flashes per second" threshold. It is also, per `ARCHITECTURE §5.50`, **not even rendered on the shipped Strudel path**.
- The note-highlight decoration ([`StrudelEditor.tsx:38`](../src/components/organisms/StrudelEditor.tsx)) does update at up to ~8 Hz on fast patterns, which exceeds 3 Hz — but 2.3.1's general flash threshold applies to areas larger than ~25 % of 10° of visual field. Inline highlights on individual characters are far below that. **Not a 2.3.1 failure**, and it is essential to the product (it is *how live coding shows you what is sounding*), so 2.2.2's essential-activity exception applies while playing.

The genuine failure is decorative motion that ignores an explicit user preference and runs when nothing is happening.

**Fix (all three are cheap, and P2-1c is a straight battery win):**
1. In `CanvasVisualizer`, read `matchMedia('(prefers-reduced-motion: reduce)')` and, when set, render **one static frame** instead of looping.
2. Gate the loop on `document.hidden` via a `visibilitychange` listener.
3. Gate the loop on `isPlaying` — the analyser-fed panels draw a module-level `EMPTY_WAVEFORM` when idle anyway, so 60 fps of redrawing a constant is pure waste.

### P2-2 · `heading-order` — 12 nodes across 6 routes

**Rule:** `heading-order` (moderate) · `/`, `/landing`, `/samples`, `/examples`, `/docs`, `/docs/:id`, both viewports

## 2 · The hard problem — what is actually reachable in a canvas-and-keyboard IDE

This is the section worth the most thought, so it gets the most honesty. A live-coding IDE is not a document. Some of it is genuinely, permanently inaccessible to a screen-reader user, and filing "add an `aria-label`" tickets against those surfaces would be theatre. Below, each surface gets a verdict and a **minimum honest remedy** — which is sometimes "provide a different control", not "annotate this one".

| Surface | Verdict | Why |
|---|---|---|
| **CodeMirror 6 editor** | **Reachable — fix it properly** | The one surface that should reach full AA |
| **Transport / toolbar / panels / Knobs** | **Reachable — fix it properly** | Ordinary controls |
| **Canvas visualizers** (waveform, spectrum, timeline, spiral, pitchwheel, punchcard) | **Not reachable — needs an equivalent, not a label** | Real-time audio-reactive graphics |
| **Piano roll** (drag note editing) | **Partially reachable** | Its edits are visual-only anyway |
| **Node graph** (React Flow) | **Not reachable on the default engine — because it is empty** | Dead surface for Strudel |
| **Virtual keyboard** | **Partially reachable** | Pointer/QWERTY only |

### 2.1 CodeMirror editor — **reachable, and the target is full AA**

CM6 has genuinely good a11y affordances. This repo configures **almost none** of them.

Configured today: `role="textbox"`, `aria-multiline`, focus management, Escape-then-Tab hatch — all CM6 defaults, none of them chosen.

Missing, all supported and cheap:
- `aria-label` via `EditorView.contentAttributes` (**P1-4**)
- `EditorView.announce` — CM6's built-in live-region effect. This is the single highest-value unused feature: it is how you announce "3 patterns playing", "evaluation error on line 4", "muted d1" to a screen reader. The app currently announces **nothing** on evaluate.
- Errors are painted into `ErrorBar` with no `role="alert"` / `aria-live` — verify and add.
- `@codemirror/search` panel labels are default English regardless of the app's locale.

**Verdict: fully achievable AA. Treat any remaining gap here as a normal bug.**

### 2.2 Canvas visualizers — **not reachable; the honest remedy is an equivalent, not ARIA**

**File:** [`src/components/atoms/CanvasVisualizer.tsx:66`](../src/components/atoms/CanvasVisualizer.tsx)

```tsx
<canvas role="img" aria-label={ariaLabel ?? 'Audio visualizer'} />
```

**Measured on `/editor`:** two canvases, **both** announcing the identical static string `"Audio visualizer"`.

This *passes* axe and *passes* the letter of WCAG 1.1.1 — non-text content has a text alternative that identifies it. It is also, functionally, worth nothing: a static label on a surface whose entire information content is that it changes 60 times a second. A blind user learns that an audio visualizer exists and nothing else, forever.

**Do not file "improve the aria-label".** No string describes a live spectrum. The honest remedies, in order of value:

1. **Make them honestly decorative.** These panels visualise audio the user is *already hearing*. That is the definition of a redundant, decorative presentation of content available through another sense. Mark the canvases `aria-hidden="true"` and label the **panel** (`<section aria-label="Waveform visualiser (visual only)">`). This is more honest than a fake label and removes noise from the AT tree.
2. **Provide the equivalent where the data is genuinely unique.** `PatternTimeline` and the piano roll show *structure* (what is playing, when) that is not otherwise available. Expose that as a live text/DOM equivalent — an `aria-live="polite"` region, updated on pattern change (not per frame), reading e.g. "4 patterns: bd*4, hh*8, bass, lead". The data already exists: `repl.state.pattern` is queried every frame by the pattern-fed visualizers.
3. **Say so in the conformance statement.** "Visualiser panels are a decorative rendering of audio output; equivalent structural information is available in the pattern list."

### 2.3 Piano roll — **partially reachable, and the ceiling is set by the product**

**Files:** [`PianorollVisualizer.tsx:277-292`](../src/components/organisms/PianorollVisualizer.tsx), [`src/lib/visualizers/pianoroll.ts`](../src/lib/visualizers/pianoroll.ts)

- **Reachable today:** the zoom/reset controls are real `<button>`s with `t()`-translated `aria-label`s, inside `role="group" aria-label="Piano roll zoom controls"`. Good work — that part is done right.
- **Not reachable:** note editing. Velocity and pitch are changed by dragging on the canvas, hit-tested against `eventSinkRef`. There is no `tabIndex`, no `role`, no `onKeyDown` on the drawing surface. WCAG 2.1.1 (Keyboard) and 2.5.7 (Dragging Movements, AA in 2.2) both apply.

**The mitigating fact that decides the remedy:** per `ARCHITECTURE §2.3`, velocity and pitch overrides are **visual only and are never written back to the code**. So this is not an editor a keyboard user is locked out of — it is a preview nobody's edits survive.

**Honest remedy:** do **not** build a keyboard note-editing mode for a surface whose edits are discarded. Either (a) mark the drag interaction as a non-essential preview and document it, or (b) if drag-editing is to become real (writing back to the document), then it needs a keyboard equivalent from day one — and the natural one already exists: **the code**. Editing `.gain(0.8)` in CodeMirror *is* the accessible equivalent of dragging a velocity bar, and it is fully keyboard reachable. Say that explicitly in the docs.

### 2.4 Node graph — **not reachable, and on the default engine there is nothing there**

**File:** [`src/components/organisms/NodeGraph.tsx`](../src/components/organisms/NodeGraph.tsx) — `grep` for `aria-`, `tabIndex`, `role=`, `onKeyDown` returns **zero hits**.

React Flow 12 ships keyboard a11y by default (focusable nodes, arrow-key movement) unless `disableKeyboardA11y` is set, so nodes are *technically* focusable — but they carry no accessible names.

The decisive fact: per `ARCHITECTURE §2.3`, `parseStrudel()` returns the whole file as **one opaque block with zero connections**, so for `strudel` (the default engine) and `midi`, **the node graph is a permanent empty state.** There is no graph to navigate.

**Honest remedy:** nothing to do for the default engine — you cannot make an empty panel accessible. For `tonejs`/`webaudio`, give `EngineNode` an accessible name and verify React Flow's keyboard mode. Low priority: this is a minor surface on two non-default engines. **Do not file a "make the node graph keyboard accessible" epic** — it would be work against a feature that does not exist for most users.

### 2.5 Virtual keyboard — **partially reachable**

**File:** [`src/components/atoms/VirtualKeyboard.tsx`](../src/components/atoms/VirtualKeyboard.tsx)

- **Reachable:** the QWERTY binding (`a w s e d f t g y h u j`) is a genuine keyboard path to playing notes, and it correctly bails on `INPUT`/`TEXTAREA`/`contenteditable` and on modifier keys (`:203`) — **it is better-behaved than `onKey`**, see P1-2.
- **Not reachable:** the on-screen keys are pointer-only (`onPointerDown`/`onPointerLeave`); they are not focusable and have no `role`/`aria-label`.
- **WCAG 2.1.4** applies to the QWERTY binding: single-character shortcuts with no remap and no way to turn them off.

**Honest remedy:** make the on-screen keys real `<button role="button" aria-label="C4">` elements (they are already discrete DOM nodes — this is cheap and genuinely useful), and add an on/off toggle for the QWERTY binding to satisfy 2.1.4.

### 2.6 What a defensible conformance claim looks like

> Live Music Coder conforms to WCAG 2.2 Level AA across its informational pages. The live-coding editor conforms to Level AA for all text, controls and code-editing functions. **Real-time audio visualisation panels are excluded** as a decorative rendering of audio the user is concurrently hearing; the equivalent structural information is available as text. Note editing by dragging in the piano roll is a visual preview that does not modify the document; the equivalent and authoritative control is the code editor itself, which is fully keyboard accessible.

That is defensible under BFSG/EN 301 549. "The whole app is AA" would not be.
